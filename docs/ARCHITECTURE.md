# Архитектура

## Что это

Мобильное веб-приложение городского фото-квеста. Команды получают
задания, снимают фотографии, отправляют их на проверку; часть
проверок автоматическая, спорное решает организатор. Баллы и
рейтинг считаются на сервере.

Масштаб задан жёстко и осознанно: **до 10 команд, до 40
участников, 30–50 заданий, до 500 фотографий, одно активное
мероприятие**. Почти все решения ниже объясняются этими цифрами.

## Стек

| Слой | Решение | Почему |
|---|---|---|
| Приложение | Next.js 16, App Router, React 19 | Один процесс на фронт и бэк. Server Actions убирают отдельный API-слой там, где он не нужен |
| Язык | TypeScript strict + `noUncheckedIndexedAccess` | Массивы и `Record` перестают врать про существование элемента |
| Стили | Tailwind CSS v4 | Токены дизайн-системы живут в `@theme` — одно место правды |
| База | Supabase PostgreSQL | Логика целостности в SQL, а не в приложении |
| Аутентификация | Supabase Auth (админ), свои сессии (участники) | Участнику не нужен аккаунт ради одного вечера |
| Хранилище | Supabase Storage, приватные бакеты | Фотографии не должны быть доступны по прямой ссылке |
| Проверка | Gemini API с image input | Опциональна, приложение работает и без неё |
| Очередь | Таблица в Postgres | На 500 задач Redis — лишний сервис, который может упасть |
| Хостинг | Vercel + Supabase | Бесплатных тарифов достаточно |

## Поток данных

### Регистрация команды

```
браузер → registerTeamAction
            ├── Zod-валидация
            ├── лимит частоты (Postgres)
            ├── crypto.randomBytes → кандидаты кодов
            └── register_team(...)          ← advisory-лок на мероприятие
                  ├── проверка статуса и окна регистрации
                  ├── проверка лимита команд
                  ├── teams + team_members + consents + team_sessions
                  └── возврат join_code
          ← httpOnly cookie с подписанным токеном
```

Лок — ключевой момент. `SELECT COUNT(*)` с последующим `INSERT`
даёт одиннадцатую команду при одновременных запросах; проверено
тестом с двадцатью параллельными соединениями.

### Отправка фотографии

```
1. браузер: сжатие          canvas → EXIF отброшен, ≤1600px, WebP
2. POST /api/submissions/start
     create_submission_slot   ← проверки: статус события, активность
                                задания, лимит попыток, идемпотентность
     ← signed upload URL + submissionId
3. браузер → Supabase Storage (по подписанной ссылке)
4. POST /api/submissions/confirm
     проверка геопозиции (если требуется)
     скачивание файла → pHash → поиск похожих → превью
     confirm_submission     ← решение: accepted | pending | manual_review
     after(): запуск воркера
   ← «Фото загружено и отправлено на проверку»
```

Строка создаётся до файла, потому что путь в хранилище строится
из её идентификатора. Клиент никогда не передаёт путь: иначе
можно было бы записать файл в каталог чужой команды.

### Проверка

```
validation_jobs (queued)
  ↓ claim_validation_jobs   ← FOR UPDATE SKIP LOCKED, пачка ≤ AI_MAX_CONCURRENCY
  ↓ submission → checking
  ↓ Gemini (structured JSON, таймаут AI_REQUEST_TIMEOUT_MS)
  ↓ decide(result, порог мероприятия)
  ├── accept        → accept_submission → score_transactions
  └── manual_review → mark_submission_manual_review
  ↓ complete_validation_job
```

Обработчик запускается тремя способами: `after()` сразу после
ответа участнику, Vercel Cron раз в минуту, кнопка в админке.

## Ключевые решения

### Баллы — журнал, а не счётчик

`teams.total_score` не существует. Сумма считается по
`score_transactions`. Отмена не удаляет строку, а добавляет
обратную и связывает их через `reverses_transaction_id` /
`reversed_by_transaction_id`.

Причина: результат квеста должен быть объяснимым через месяц.
Счётчик отвечает «сколько», журнал отвечает «почему».

Идемпотентность обеспечена частичным уникальным индексом:

```sql
CREATE UNIQUE INDEX ON score_transactions (submission_id)
  WHERE transaction_type = 'task_accepted'
    AND reversed_by_transaction_id IS NULL;
```

Одна действующая транзакция на отправку. После отмены индекс
освобождается, и задание можно принять заново.

### Сессии участников

Ни email, ни пароля. В cookie лежит `<токен>.<подпись>`:

- токен — 32 случайных байта;
- подпись — HMAC-SHA256 на `SESSION_SECRET`;
- в базе — только SHA-256 от токена.

Подпись отсекает мусор до похода в базу. Хранение хэша означает,
что утечка `team_sessions` не даёт войти ни в одну команду.
Идентификатора команды в cookie нет вообще, поэтому подменить
её редактированием куки невозможно.

### Очередь в базе

Требование ТЗ — обойтись без платного брокера. Таблица
`validation_jobs` плюс `FOR UPDATE SKIP LOCKED` дают всё нужное:
несколько обработчиков разбирают разные строки не мешая друг
другу, зависшие задачи возвращаются по `AI_STALE_CHECK_MINUTES`,
повторный запуск безопасен.

При 500 фотографиях очередь разбирается пачками по
`AI_MAX_CONCURRENCY` (по умолчанию 4), а не 500 параллельными
запросами к модели.

### Границы AI

Модель может **принять** или **отдать человеку**. Отклонить —
никогда. Любой сбой, таймаут или неразобранный ответ означает
`manual_review`, а не отказ участнику.

В запрос не уходят имена участников, название команды и
контакты. Системная инструкция прямо запрещает опознавать людей
и рассуждать о чувствительных характеристиках.

### Обновление статусов — опрос, а не Supabase Realtime

**Это отступление от ТЗ, и оно сознательное.** Раздел 34
требует Supabase Realtime; вместо него сделан адаптивный опрос
(`components/game/live-refresh.tsx`).

Почему. Клиентская подписка Realtime на `submissions` означает,
что браузер участника получает токен с правом читать таблицу
отправок напрямую. Приложение построено на обратном принципе:
участник вообще не обращается к базе, всё идёт через сервер,
который знает команду из httpOnly cookie. Ради секунд задержки
пришлось бы выдать браузеру долгоживущий JWT и расширить
поверхность атаки на самую чувствительную таблицу.

Что сделано вместо. Экран сам вызывает `router.refresh()`:

- каждые 20 секунд, **только пока есть отправки в работе**;
- при возврате на вкладку — телефон в кармане глушит таймеры;
- при восстановлении связи.

Когда ждать нечего, запросов нет вовсе. Задержка — до 20 секунд
против «мгновенно»; на квесте, где после отправки прямо
предлагается идти дальше, разница незаметна.

Дверь оставлена открытой: политики RLS уже написаны через
`current_team_id()` из claim `team_id`, поэтому включение
Realtime не потребует менять схему — только выдавать токен.

### Работа при плохой связи

- Подготовленный файл сохраняется в IndexedDB **до** отправки.
- Повтор использует тот же ключ идемпотентности — второй
  отправки не возникает.
- Service worker кэширует оболочку и картинки; страницы идут
  network first, чтобы статус не показывался вчерашним.
- `/api/*` и `/admin/*` не кэшируются никогда.

## Модель доступа

| Роль | Как определяется | Что может |
|---|---|---|
| Посетитель | нет cookie | Главная, правила, публичный рейтинг |
| Участник | подписанная cookie → `team_sessions` | Свои задания, свои отправки, свой прогресс |
| Капитан | `team_members.is_captain` | То же плюс состав команды до старта |
| Администратор | Supabase Auth + строка в `admin_users` | Всё |

Участники **никогда не пишут в базу напрямую** — у них нет ни
одной политики INSERT/UPDATE/DELETE. Запись выполняет сервер
после проверки сессии.

Роль администратора проверяется по таблице, а не по метаданным
токена: строку в таблице пользователь изменить не может.

## Отказоустойчивость

| Что отказало | Что происходит |
|---|---|
| Gemini недоступен | Фотографии уходят в ручную проверку, квест идёт |
| Квота исчерпана | То же, плюс видно в сводке |
| Обработчик завис | Задачи возвращаются в очередь по таймауту |
| Плохая связь у участника | Черновик в IndexedDB, повтор без дублей |
| Ошибка счётчика лимитов | Запрос пропускается, гарантии даёт база |
| Сбой записи в журнал действий | Действие всё равно выполняется |

Полный план — в [INCIDENT_PLAN.md](./INCIDENT_PLAN.md).

## Что намеренно не сделано

- **Онлайн-оплата.** Организатор принимает деньги сам.
- **Мультиарендность.** Схема допускает несколько мероприятий,
  но интерфейс работает с одним.
- **Микросервисы, Redis, брокеры.** На этом масштабе они добавляют
  точки отказа, а не устойчивость.
- **Интерактивная карта.** Геопозиция проверяется, но карты нет:
  задания и так привязаны к узнаваемым местам.
- **Zip-архив фотографий из браузера.** 400 МБ не соберутся в
  serverless-функции; выгрузка делается через Supabase CLI.
