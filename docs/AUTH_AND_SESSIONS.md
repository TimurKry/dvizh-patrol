# Аутентификация и сессии

В приложении две независимые схемы входа: для участников и для
организатора. Они не пересекаются.

## Участники: сессия без аккаунта

Заводить учётную запись ради одного вечера бессмысленно.
Участнику не нужны ни email, ни пароль.

### Устройство токена

```
cookie:  <токен>.<подпись>

токен   = 32 случайных байта (crypto.randomBytes), base64url
подпись = HMAC-SHA256(SESSION_SECRET, токен), base64url
в базе  = SHA-256(токен) в team_sessions.token_hash
```

Три свойства, ради которых это сделано именно так:

**Cookie непрозрачна.** Идентификатора команды в ней нет вообще.
Отредактировать её и стать другой командой невозможно — там
просто нечего редактировать.

**Подпись отсекает мусор до базы.** Подобранное значение
отбрасывается на HMAC, запрос к Postgres не уходит. Сравнение
постоянное по времени (`timingSafeEqual`).

**В базе только хэш.** Утечка `team_sessions` не даёт войти ни в
одну команду: из SHA-256 токен не восстановить.

Код: `lib/session/token.ts` (чистая криптография, покрыта
тестами) и `lib/session/team-session.ts` (работа с cookie и базой).

### Параметры cookie

```
httpOnly: true          недоступна из JavaScript
sameSite: 'lax'         защита от CSRF при переходах
secure:   в проде       только по HTTPS
maxAge:   TEAM_SESSION_TTL_HOURS × 3600
```

### Как получают сессию

При **создании команды**: капитан вводит название, своё имя и
контакт, принимает правила, отдельно решает вопрос о публикации
фотографий. Сервер создаёт команду, капитана, согласие и сессию —
всё в одной транзакции.

При **входе по коду**: участник вводит шестизначный код и имя.
Если участник с таким именем уже есть, новое место в команде не
занимается — просто выдаётся новая сессия. Это нормальный
сценарий: человек потерял cookie и заходит снова.

### Как проверяется

`getTeamSession()` — единственный способ узнать текущую команду
на сервере:

1. читает cookie;
2. проверяет подпись;
3. ищет `token_hash` в базе;
4. проверяет `revoked_at` и `expires_at`;
5. проверяет, что команда не отменена;
6. возвращает команду, участника и мероприятие.

**Ни один обработчик не принимает `team_id` от клиента.**
Отправки, задания, баллы — всё привязывается к команде из
сессии.

Отметка активности (`last_seen_at`) обновляется не чаще раза в
пять минут: писать в базу на каждый запрос незачем.

### Отзыв

- Участник нажимает «Выйти» → `revoked_at` у его сессии.
- Организатор нажимает «Сбросить сессии» → отзываются все
  сессии команды.
- Капитан удаляет участника до старта → отзываются его сессии.

Отзыв работает по-настоящему: удалить cookie недостаточно, если
телефон потеряли.

## Организатор: Supabase Auth

Вход по email и паролю через Supabase Auth.

**Наличие сессии Supabase прав не даёт.** После успешного входа
проверяется строка в `admin_users`; если её нет — сессия
немедленно закрывается.

Роль хранится в таблице, а не в метаданных токена: метаданные в
некоторых схемах пользователь может изменить сам, строку в
таблице — нет.

```
lib/auth/admin.ts
  getAdmin()      → контекст администратора или null
  requireAdmin()  → контекст или редирект на /admin/login
  audit()         → запись в журнал
```

`middleware.ts` обновляет токен Supabase на маршрутах `/admin/*`:
серверный компонент не может писать cookie. **Права там не
проверяются** — это делает `requireAdmin()` на самой странице.
Middleware как единственный барьер — известный источник дыр.

### Создание администратора

```bash
node scripts/create-admin.mjs you@example.com "надёжный-пароль"
```

Скрипт заводит пользователя в Supabase Auth и добавляет строку в
`admin_users`. Без второго шага вход бесполезен.

## Ограничение частоты

Счётчики фиксированного окна в Postgres (`rate_limits`).

| Действие | Окно | Лимит |
|---|---|---|
| Создание команды | 10 мин | 8 |
| Вход по коду | 10 мин | 15 |
| Создание отправки | 1 мин | 20 на команду |
| Повтор проверки | 1 мин | 30 |
| Вход администратора | 15 мин | 10 |

Лимит отправок считается **по команде**, а не по адресу: четыре
человека за одним мобильным NAT не должны блокировать друг друга.

Ограничение по адресу — защита от случайного шторма и грубого
перебора, не от целенаправленной атаки: заголовок
`x-forwarded-for` подделывается. Настоящие гарантии дают
уникальные ограничения в базе.

Сбой счётчика **пропускает** запрос: неработающий лимитер не
должен останавливать мероприятие.

## Что где хранится

| Данные | Где | Заметка |
|---|---|---|
| Токен сессии | cookie браузера | httpOnly, подписан |
| Хэш токена | `team_sessions` | SHA-256, не обратим |
| Сессия админа | cookie Supabase | Управляется `@supabase/ssr` |
| Роль админа | `admin_users` | Не в токене |
| Ключ service_role | переменная окружения | Только сервер, модули `server-only` |
| Ключ Gemini | переменная окружения | Только сервер |

Ни один секрет не имеет префикса `NEXT_PUBLIC_`. Модули с
секретами помечены `server-only` — импорт из клиентского
компонента ломает сборку.
