# Очередь проверок

## Почему в базе

Требование ТЗ — обойтись без платного брокера. Но дело не только
в деньгах: на 500 задач за вечер Redis или внешняя очередь
добавляют ещё один сервис, который может отказать посреди
мероприятия, и ещё один набор состояний, который надо
синхронизировать с базой.

Postgres уже есть, уже транзакционен и уже умеет `FOR UPDATE
SKIP LOCKED`. Этого достаточно.

## Таблица

```sql
validation_jobs (
  id, submission_id UNIQUE, status, attempts,
  available_at, locked_at, locked_by,
  last_error, completed_at, created_at, updated_at
)
```

Статусы: `queued → processing → completed | failed`, плюс
`cancelled` для аварийного сценария.

Индексы частичные — очередь опрашивается часто:

```sql
CREATE INDEX ON validation_jobs (available_at) WHERE status = 'queued';
CREATE INDEX ON validation_jobs (locked_at)    WHERE status = 'processing';
```

## Жизненный цикл

```
загрузка подтверждена
  └── confirm_submission → submission = pending
                         → validation_jobs = queued

обработчик
  └── claim_validation_jobs(worker, limit, stale)
        ├── возвращает в очередь зависшее
        ├── SELECT ... FOR UPDATE SKIP LOCKED LIMIT n
        ├── status = processing, attempts + 1
        └── submission = checking

  └── скачивание файла → Gemini → decide()
        ├── accept        → accept_submission → баллы
        └── manual_review → mark_submission_manual_review

  └── complete_validation_job
```

## Как запускается

Три способа, и все три нужны:

**`after()` после ответа участнику.** Проверка стартует сразу,
не задерживая ответ. Участник уже получил «можно продолжать
квест», а обработка идёт в том же вызове функции.

**Vercel Cron.** Подбирает то, что не успело, и зависшее.
Настроен в `vercel.json` на раз в сутки — чаще тариф Hobby
не разрешает, деплой с минутным расписанием он просто не
создаёт. Для минутного нужен Pro или внешний планировщик,
дёргающий тот же путь с заголовком `x-worker-secret`.

Основную работу всё равно делает `after()`: cron — страховка,
а не главный путь.

**Кнопка в админке.** «Повторно обработать зависшие» —
`requeue_stale_validations` плюс немедленный проход.

## Гарантии

### Параллельные обработчики не мешают друг другу

`SKIP LOCKED` означает: если строка заблокирована другим
обработчиком, она пропускается, а не ожидается. Два вызова
разбирают разные задачи и не блокируются.

Проверено тестом: восемь задач, два обработчика по четыре —
пересечений нет.

### Зависшее возвращается

Обработчик может умереть, не сняв блокировку: истёк лимит
времени функции, упал контейнер. Задачи в `processing` с
`locked_at` старше `AI_STALE_CHECK_MINUTES` возвращаются в
очередь при следующем проходе.

### Повтор не начисляет дважды

Ключевая гарантия. Даже если задача обработается дважды,
`accept_submission` идемпотентна: частичный уникальный индекс
допускает одну действующую транзакцию `task_accepted` на
отправку.

Проверено тестом: восемь параллельных принятий → 50 баллов, одна
строка в журнале.

### Очередь не сжигает квоту

Пачка ограничена `AI_MAX_CONCURRENCY` (по умолчанию 4, диапазон
1–6). При 500 фотографиях очередь разбирается постепенно, а не
пятьюстами одновременными запросами.

## Повторы при ошибке

```
attempts < AI_MAX_ATTEMPTS   → status = queued,
                                available_at = now() + 20 сек
attempts >= AI_MAX_ATTEMPTS  → status = failed,
                                submission → manual_review (ai_error)
```

Отправка не теряется никогда: худший исход — она попадает к
организатору.

## Что видит организатор

На сводке:

- ожидают проверки;
- проверяются;
- ручная проверка;
- задач с ошибкой;
- задач в очереди.

Кнопка «Обработать зависшие» показывает, сколько вернулось в
очередь и сколько отправок освободилось.

## Ограничения

**Vercel Cron — не чаще раза в минуту.** Это верхняя граница
задержки для отправок, которые не успел подхватить `after()`.

**Лимит времени функции.** `/api/worker/validate` объявляет
`maxDuration = 120`. Пачка из четырёх снимков с таймаутом 20
секунд укладывается с запасом.

**Один обработчик за вызов.** Специально: несколько
одновременных проходов упёрлись бы в квоту модели. Если нужно
быстрее — поднимите `AI_MAX_CONCURRENCY` до 6.

## Ручной запуск

```bash
curl -X POST https://ваш-домен/api/worker/validate \
  -H "x-worker-secret: $WORKER_SECRET"
```

Ответ:

```json
{"ok":true,"claimed":4,"accepted":3,"manualReview":1,
 "failed":0,"skipped":0,"durationMs":5230}
```

Запрос без секрета отклоняется с кодом 403. Если `WORKER_SECRET`
не задан, эндпоинт закрыт полностью.
