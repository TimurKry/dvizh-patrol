# Приватность: как это устроено технически

Пользовательская версия — на странице `/privacy` в приложении.
Здесь — реализация.

## Что собирается

| Данные | Где | Зачем | Срок |
|---|---|---|---|
| Название команды | `teams.name` | Рейтинг | Бессрочно |
| Имя капитана | `teams.captain_name` | Связь | Бессрочно |
| Контакт капитана | `teams.contact` | Связь до старта | Бессрочно |
| Имена участников | `team_members.name` | Состав команды | Бессрочно |
| Фотографии | Storage, приватный бакет | Подтверждение заданий | `photo_retention_days` |
| Геопозиция | `submissions.latitude/longitude` | Только для заданий с привязкой | С отправкой |
| Технические данные сессии | `team_sessions` | Работа входа | TTL сессии |
| Согласия | `consents` | Юридическое основание | Бессрочно |

Email и паролей участников нет вообще: учётной записи в привычном
смысле не существует.

## Метаданные фотографий

Снимок пересжимается **в браузере** до отправки:
`createImageBitmap` с `imageOrientation: 'from-image'`, отрисовка
на canvas, кодирование в WebP.

Перерисовка через canvas отбрасывает EXIF целиком. На сервер не
попадают:

- координаты съёмки;
- модель камеры и телефона;
- время съёмки;
- серийные номера;
- прочие теги.

Это побочный эффект сжатия, но эффект намеренный: код
задокументирован именно так, чтобы его не «оптимизировали»
обратно.

Координаты, которые всё же сохраняются, приходят отдельно из
Geolocation API и только для заданий с `require_location = true`.

## Доступ к фотографиям

Бакет `submission-images` приватный. Прямой ссылки не существует.

```
events/{eventId}/teams/{teamId}/tasks/{taskId}/{submissionId}.webp
```

Файл отдаётся только по подписанной ссылке с ограниченным сроком
(`SIGNED_URL_TTL_SECONDS`, по умолчанию час).

Кто может получить ссылку:

- команда — на свои отправки;
- организатор — на все.

Другие команды не могут получить ни ссылку, ни строку из базы:
политика RLS ограничивает `submissions` по `current_team_id()`.

Клиент никогда не выбирает путь для записи — его строит сервер.
Иначе можно было бы записать файл в каталог чужой команды.

## Автоматическая проверка

Что уходит в Gemini:

- текст задания и критерии;
- минимальное число людей;
- изображение;
- эталон, если есть.

Что **не** уходит: имена, название команды, контакты,
идентификаторы, координаты.

Системная инструкция прямо запрещает опознавать людей, сравнивать
лица, определять возраст, происхождение, здоровье и любые
чувствительные характеристики. Людей модель описывает
обезличенно.

Проверка отвечает на один вопрос: соответствует ли фотография
условиям задания.

Полностью отключается флажком в настройках мероприятия либо
отсутствием ключа.

## Два разных согласия

```sql
CHECK (participation_consent AND photo_processing_consent)
```

Участие невозможно без согласия на обработку фотографий: без
снимков квест не работает.

```sql
social_publication_consent boolean NOT NULL DEFAULT false
```

Публикация в соцсетях — **отдельный флажок без ограничения**. Его
можно не ставить, и на участие это не влияет.

Разделение сделано на уровне схемы намеренно: одна галочка «я на
всё согласен» — плохая практика.

Перед публикацией выгрузите `/api/admin/export/consents` и
сверьтесь.

## Версионирование согласий

`consents.policy_version` хранит версию политики на момент
согласия (`POLICY_VERSION`). При изменении условий видно, кто на
что соглашался.

## Хранение и удаление

`events.photo_retention_days` задаёт срок и **показывается
участникам** на странице о конфиденциальности.

`/admin/settings` → «Удалить просроченные фотографии»:

1. находит отправки старше срока;
2. удаляет файлы из обоих бакетов;
3. обнуляет `image_path` и `preview_path`;
4. **оставляет записи об отправках**.

Последнее принципиально: удаление записей разорвало бы журнал
начислений, и итог квеста стал бы невоспроизводимым. Удаляются
персональные данные (изображения), а не факт начисления.

## Удаление по запросу

Отдельной кнопки нет — на 40 участников это делается вручную:

```sql
-- фотографии команды
UPDATE submissions SET image_path = NULL, preview_path = NULL
WHERE team_id = '...';
-- сами файлы удаляются из Storage отдельно

-- контакт
UPDATE teams SET contact = NULL WHERE id = '...';

-- участник
DELETE FROM team_members WHERE id = '...';
```

Баллы при этом сохраняются: результат квеста не переписывается.

## Безопасность секретов

| Секрет | Где | Защита |
|---|---|---|
| `SUPABASE_SERVICE_ROLE_KEY` | сервер | Модуль `server-only`, нет `NEXT_PUBLIC_` |
| `SESSION_SECRET` | сервер | То же |
| `GEMINI_API_KEY` | сервер | То же, запрос только с сервера |
| `WORKER_SECRET` | сервер | Сравнение постоянное по времени |
| Токен сессии | cookie | httpOnly, подписан, в базе только хэш |

`lib/env.ts` помечен `server-only`: импорт из клиентского
компонента ломает сборку. Утечка ключа в браузерный бандл
невозможна по построению, а не по договорённости.

## Геопозиция

Приложение спрашивает местоположение в трёх случаях, и каждый раз
по конкретному поводу:

| Когда | Что происходит |
|---|---|
| Задание требует места | Координаты уходят на сервер вместе с отправкой и сохраняются: по ним проверяется радиус зачёта |
| Включён строгий режим игрового поля | То же самое, но для каждой фотографии |
| Нажата кнопка «Где я» на карте | Точка рисуется в браузере и **никуда не отправляется** |

Кнопка «Где я» делает один запрос и забывает результат при
перезагрузке страницы. Постоянного слежения (`watchPosition`) нет
нигде.

Координаты отправки — **заявленные**: они приходят с телефона, и
сервер им не доверяет, а использует только чтобы решить, засчитать
снимок или показать организатору.

Подложка карты грузится с серверов OpenStreetMap. Им, как и
любому серверу картинок, виден IP-адрес и то, какие квадраты
карты запрошены. Ни кто вы, ни в какой вы команде — не передаётся.

## Чего в приложении нет

- Аналитики и трекеров.
- Сторонних скриптов.
- Рекламных пикселей.
- Постоянного отслеживания геопозиции — только разовые запросы
  по поводам из таблицы выше.
- Передачи данных третьим лицам, кроме Gemini для проверки и
  серверов тайлов OpenStreetMap для подложки карты.
- Профилирования участников.
