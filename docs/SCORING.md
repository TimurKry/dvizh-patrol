# Баллы и рейтинг

## Журнал вместо счётчика

Поля `teams.total_score` **не существует**. Это не упущение.

Счётчик отвечает на вопрос «сколько». Журнал отвечает на вопрос
«почему». Через месяц после квеста второй вопрос оказывается
важнее: команда спорит о результате, и нужно показать, за что
именно начислено.

```sql
SELECT sum(points) FROM score_transactions WHERE team_id = ...
```

На десяти командах и пятистах отправках это дешевле, чем
поддерживать согласованность денормализованного счётчика.

## Типы транзакций

| Тип | Кто создаёт | Знак |
|---|---|---|
| `task_accepted` | Проверка или организатор | + |
| `manual_adjustment` | Организатор | любой |
| `bonus` | Организатор | + |
| `penalty` | Организатор | − |
| `submission_revoked` | Отмена принятого решения | − |

Знак у бонуса и штрафа выводится из типа, а не из ввода:
«оштрафовать на +50» невозможно.

Причина обязательна для всех ручных операций.

## Идемпотентность

```sql
CREATE UNIQUE INDEX ON score_transactions (submission_id)
  WHERE transaction_type = 'task_accepted'
    AND reversed_by_transaction_id IS NULL;
```

Одна **действующая** транзакция начисления на отправку. Слово
«действующая» здесь ключевое: после отмены индекс освобождается,
и задание можно принять заново.

`accept_submission` перед вставкой проверяет наличие действующей
транзакции под блокировкой строки отправки. Повторный вызов
возвращает существующую и не начисляет второй раз.

Проверено тестом: восемь параллельных принятий → 50 баллов.

## Отмена

Старая транзакция **не удаляется**. Создаётся обратная:

```
исходная:  +50  task_accepted        reversed_by → обратная
обратная:  −50  submission_revoked   reverses   → исходная
```

Сумма становится нулём, обе строки остаются в журнале.

Отправка переходит в `rejected`, `awarded_points` обнуляется.
Если у команды остались попытки, она может отправить другую
фотографию.

Повторная отмена безопасна: действующей транзакции больше нет,
функция ничего не делает и счёт не уходит в минус.

## Полный цикл

```
принято      +50   →  50
отменено     −50   →   0
принято      +50   →  50   (новая транзакция, индекс освободился)
бонус        +20   →  70
штраф        −10   →  60
```

В журнале пять строк. Каждая объяснима.

## Рейтинг

Сортировка (раздел 33 ТЗ):

1. сумма баллов, по убыванию;
2. число принятых заданий, по убыванию;
3. время последнего принятого задания, по возрастанию.

Третий критерий даёт преимущество тем, кто набрал столько же
раньше.

```sql
row_number() OVER (
  PARTITION BY event_id
  ORDER BY total_points DESC,
           accepted_count DESC,
           last_accepted_at ASC NULLS LAST
)
```

Отменённые команды в рейтинг не попадают.

## Режимы показа

| Режим | Что видит участник |
|---|---|
| `public` | Полную таблицу |
| `team_position_only` | Только своё место и баллы |
| `hidden` | Ничего |
| `frozen` | Сохранённый снимок |

Фильтрация выполняется **на сервере**, в
`lib/data/leaderboard.ts`. Отдать лишние строки и спрятать их
разметкой — не вариант.

### Заморозка

`freeze_leaderboard` сохраняет снимок в
`leaderboard_snapshots` и переключает режим.

После этого участники видят зафиксированную таблицу, а
организатор — и снимок, и реальное положение дел. Начисления
продолжают работать, просто в таблице не отражаются.

Типичный сценарий: заморозить за час до финиша, чтобы интрига
дожила до объявления результатов.

Разморозка удаляет снимок и возвращает выбранный режим.

## Прогресс команды

Представление `team_progress`:

| Поле | Смысл |
|---|---|
| `tasks_total` | Активных заданий в мероприятии |
| `accepted` | Принято |
| `pending` + `checking` | На проверке |
| `manual_review` | Ждёт организатора |
| `rejected` | Отклонено |
| `tasks_touched` | Заданий, по которым что-то отправлено |

типами, суммами, причинами и отметкой об отмене.
