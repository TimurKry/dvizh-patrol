# Тесты

```bash
npm run test              # модульные (быстро, без базы)
npm run test:integration  # против живого Postgres
npm run test:all          # всё
npm run test:e2e          # Playwright, нужен Supabase
npm run verify            # typecheck + lint + тесты + сборка
```

## Что чем проверяется

| Уровень        | Файлов | Тестов | Требует               |

## Модульные

`tests/unit/` — чистая логика, без базы и сети.

| Файл                    | Что проверяет                                                                    |
| ----------------------- | -------------------------------------------------------------------------------- |
| `phash.test.ts`         | Перцептивный хэш: устойчивость к пережатию, различение картинок, поиск дубликата |
| `import.test.ts`        | Разбор CSV по RFC 4180, валидация JSON, повторы номеров, отчёт об ошибках        |
| `ai-decision.test.ts`   | Порог уверенности, разрешение противоречий, **невозможность отклонения**         |
| `geo.test.ts`           | Гаверсинус, проверка радиуса, учёт погрешности                                   |
| `session-token.test.ts` | Подпись, подмена токена, отсутствие team_id в cookie                             |
| `messages.test.ts`      | Русские склонения, полнота словаря статусов                                      |

Отдельно стоит отметить `phash.test.ts`: он генерирует
синтетические изображения, пережимает их через ресайз и WebP и
проверяет, что расстояние Хэмминга осталось в пределах порога.
Это и есть свойство, ради которого pHash взят вместо хэша файла.

И `ai-decision.test.ts`: там есть тест, который перебирает
граничные ответы модели и убеждается, что вердикт никогда не
равен «отклонить».

## Интеграционные

`tests/integration/` — против настоящего PostgreSQL.

```bash
npm run db:start     # поднять кластер
npm run db:reset     # схема + миграции
npm run test:integration
```

Скрипт поднимает чистый Postgres и накатывает shim с объектами
Supabase (`supabase/local/00-supabase-shim.sql`). Схема, функции,
ограничения и индексы при этом **ровно те**, что уедут в прод.

| Файл                            | Что проверяет                                                   |
| ------------------------------- | --------------------------------------------------------------- |
| `registration.test.ts`          | Лимиты команд и участников, гонки, правила регистрации          |
| `scoring.test.ts`               | Отправки, попытки, идемпотентность, отмена и повторное принятие |
| `queue-and-leaderboard.test.ts` | Очередь, зависшие задачи, ранжирование, заморозка               |
| `load.test.ts`                  | Полный масштаб мероприятия                                      |

### Гонки проверяются по-настоящему

Не последовательными вызовами, а параллельными соединениями:

```ts
const attempts = await Promise.all(
  Array.from({ length: 20 }, (_, i) => registerTeam(eventId, `Гонка ${i}`)),
);

expect(attempts.filter((r) => r.ok)).toHaveLength(1);
expect(attempts.filter((r) => r.error === 'event_full')).toHaveLength(19);
```

Двадцать одновременных запросов на одно свободное место —
создаётся ровно одна команда. Без advisory-лока этот тест падает.

То же для пятого участника и для двойного начисления баллов.

### Нагрузочный тест

`load.test.ts` разворачивает заявленный масштаб: 10 команд,
40 участников, 50 заданий, 500 отправок, 250 принятий.

Проверяет:

- сумма журнала совпадает с суммой по отправкам;
- ни одной отправки с двумя действующими начислениями;
- ни одного задания с двумя принятыми отправками у команды;
- рейтинг считается быстрее 1,5 с;
- очередь проверки открывается быстрее 1,5 с;
- сводка админки собирается быстрее 2 с.

## Что тесты уже нашли

Два настоящих дефекта, а не выдуманных:

**Локаль базы.** Локальный кластер поднимался с `--locale=C`, где
`lower()` не понимает кириллицу. Уникальный индекс по имени
команды пропускал «Трамвай» и «трамвай» как разные, а повторный
вход участника создавал второе место в команде. На Supabase
локаль корректная, но тестовое окружение обязано совпадать с
боевым — иначе такие тесты бесполезны.

**Приведение типов в SQL.** В запросе нагрузочного теста `text ||
uuid` без явного `::text` — оператор не определён.

## Сквозные

`e2e/` — Playwright, требует настоящего Supabase.

```bash
cp .env.example .env.local        # заполнить
node scripts/create-admin.mjs admin@test.local "пароль"
export E2E_ADMIN_EMAIL=admin@test.local
export E2E_ADMIN_PASSWORD=пароль
npm run test:e2e
```

> **Эти тесты не запускались при разработке**: у среды сборки не
> было ключа `service_role` от боевого проекта. Они написаны, но
> их первый прогон предстоит выполнить при развёртывании.

`participant.spec.ts` — регистрация, вход по коду, доступность,
PWA. Не меняет состояние мероприятия.

`quest-flow.spec.ts` — полный цикл: запуск квеста, отправка
фотографии, проверка организатором, начисление, завершение.
**Меняет состояние мероприятия** — направляйте на тестовый
проект.

Тесты ищут элементы по видимому тексту, а не по служебным
атрибутам: участник ориентируется именно по словам, и если
формулировка изменится, тест должен об этом сказать.

## Чего тесты не покрывают

Честный список:

- **Реальный вызов Gemini.** Проверяется разбор ответа и логика
  решения, но не сама модель: тест, зависящий от внешнего API,
  ломается по чужому расписанию.
- **Загрузка в Supabase Storage.** Покрыта только в e2e.
- **Сжатие в браузере.** `lib/image/compress.ts` использует
  canvas — нужен настоящий браузер, проверяется в e2e.
- **Service worker.** Проверяется вручную.
- **Визуальные регрессии.** Скриншотных тестов нет.

## Соглашения

Названия тестов — по-русски и описывают поведение, а не метод:

```
✓ одиннадцатую команду не создаёт
✓ не пробивается параллельными запросами за последнее место
✓ отмена команды освобождает место
```

Такой список читается как спецификация. Если тест назван
«тестирует registerTeam», он не объясняет, что сломалось.
